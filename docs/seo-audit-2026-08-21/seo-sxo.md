# SXO 분석 — 카공맵 (https://cagongmap-nu.vercel.app/)

대상 키워드: "송파 카공카페", "잠실 노트북 하기 좋은 카페", "콘센트 있는 카페 송파", "강남 카공맵"

## 0. 대상 페이지 팩트 (렌더링 + 파싱 결과)

- `claude-seo run render_page.py ... --mode auto`가 SPA로 판정(`is_spa: true`)했고, 초기 렌더가 안정화 임계값에 못 미쳐(`render_diagnostics`) 지도·마커 DOM은 못 잡았습니다. 그래서 `<head>`·초기 HTML은 curl로 받은 정적 셸(Next.js prerender, `x-nextjs-prerender: 1`)로 교차 확인했습니다 — Googlebot이 실제로 받는 최초 HTML과 같은 것입니다.
- Title: `카공맵 — 노트북 작업하기 좋은 카페 지도`
- Meta description: `콘센트·와이파이·소음으로 작업하기 좋은 카페를 지도에서 찾습니다.`
- **`<meta name="robots" content="noindex, nofollow"/>`** — 사진 권리 미확정으로 의도된 차단(CLAUDE.md에 명시). 이번 분석은 "차단을 풀 때를 대비한 준비도" 분석입니다.
- H1: `카공맵` 1개 — 브랜드명뿐, 의도(검색 의도와 맞는 서술)가 없습니다.
- H2: 0개, 이미지 태그: 0개(초기 HTML 기준 — 카페 사진은 지도 상호작용 이후 JS로만 나타납니다), 내부/외부 링크: 0개, **schema.org 구조화 데이터: 0개**.
- 본문 텍스트(정적): 19단어. `250m / WORK CAFE MAP / 카공맵 / 오래 앉아 작업하기 좋은 카페 9곳 / 카카오 로그인 / 카페 제보하기` 정도가 전부입니다.
- og:title/og:description/og:image는 잘 갖춰져 있습니다(공유 카드용, 검색 순위와는 별개).
- 페이지 구조: 풀스크린 지도 + 클릭 시 뜨는 상세 패널. 카페별 URL 없음, 목록 페이지 없음, 검색/필터 UI 없음(2차로 의도적 보류).

## 1. SERP 역산 분석 — 이 4개 쿼리에서 구글이 실제로 보상하는 페이지 타입

WebSearch(구글 색인 기반)로 4개 쿼리를 각각 조회한 결과, 상위 결과의 구성이 놀랍도록 일관됩니다.

| 쿼리 | 상위에 뜨는 것 |
|---|---|
| 송파 카공카페 | diningcode.com "Top100" 리스트 페이지 2개, 블라인드 자기홍보 글(경쟁 서비스 zakgong.com 언급), 매거진 카페투어 글(에스콰이어, 씨티매거진, 블랙워터이슈) |
| 잠실 노트북 하기 좋은 카페 | 인스티즈·블라인드·threads.com 커뮤니티 글, brunch.co.kr 블로그, 큐레이션 사이트 jinjja-seoul.com |
| 콘센트 있는 카페 송파 | diningcode.com 리스트 페이지 3개, 특정 카페 상세 리뷰(diningcode profile 페이지) |
| 강남 카공맵 | diningcode.com "Top68" 리스트, 틱톡/인스타그램(해시태그+캡션 텍스트), 노마드랑 게시판(nomadrang.com), 블로그(loclr.com) |

**page-type-taxonomy.md 기준 분류 결과 (SERP 컨센서스):**

- **1위 유형 — Local Page (디렉토리/리스트형)**: diningcode.com의 "Top100/Top68" 페이지가 4개 쿼리 중 3개에서 최상단을 차지. 이건 수백~수천 개 카페를 필터·평점·주소와 함께 나열하는, 크롤링 가능한 텍스트 밀도가 매우 높은 페이지입니다. **추정 비중 약 45%**.
- **2위 유형 — Blog Post (커뮤니티/매거진 리스티클)**: 블라인드·인스티즈·threads·brunch·매거진("OO곳 카페 투어") 형태가 4개 쿼리 전부에 등장. 저자 시점의 1인칭 경험담, "눈치 안 보임", "콘센트 있음" 같은 구체적 텍스트 서술이 특징. **추정 비중 약 45%**.
- **3위 — 큐레이션/보드형 콘텐츠(jinjja-seoul.com, nomadrang.com)**: Blog Post의 변형으로 취급. **약 10%**.
- **Tool/Interactive(지도 앱 자체가 결과로 뜨는 경우)**: **0%**. 카카오맵·네이버지도·경쟁 지도 서비스가 검색결과 링크 자체로 뜬 사례는 이번 조사에서 하나도 없었습니다.

**SERP 컨센서스: Local(디렉토리) + Blog(리스티클) 혼합, 신뢰도 약 90%.** 두 유형 다 공통점은 "이름·주소·구체적 속성(콘센트 유무, 몇 시까지, 자리 수)이 텍스트로 크롤링 가능하게 노출된다"는 것입니다.

### 한국 검색 지형에서 네이버의 역할 (중요 — 반드시 짚어야 함)

WebSearch는 구글 색인을 기반으로 하므로 이번 조사에서 **blog.naver.com·map.naver.com 링크가 top10에 단 한 건도 나오지 않았습니다.** 이건 실수가 아니라 구조적인 현상이고, 두 가지를 의미합니다.

1. **"OO역 카공카페" 같은 초로컬 쿼리는 한국 사용자 대다수가 애초에 네이버에서 검색합니다.** 구글이 아니라요. 이 4개 키워드에서 카공맵이 구글 상위에 오른다 해도, 실제 타겟 사용자 트래픽의 상당 부분은 네이버 검색·네이버 지도 생태계 안에서만 일어나는 별개의 전장입니다.
2. **네이버 생태계는 이 프로젝트가 구조적으로 이길 수 없는 싸움입니다.** 네이버 검색이 "카공카페" 류 쿼리에 보여주는 것은 (a) 네이버 플레이스(사업자가 직접 등록한 스마트플레이스) 카드, (b) 네이버 블로그 후기, (c) 네이버 카페 커뮤니티 글입니다. 카공맵은 큐레이션 대상 9곳의 **사업자가 아니므로** 네이버 플레이스를 대신 최적화할 권한이 없고, 네이버 블로그·카페 생태계 밖에 있는 Next.js 앱은 네이버 검색에서 구조적으로 하위권입니다.

**결론:** 구글 쪽은 "콘텐츠를 크롤링 가능하게 만들면" 경쟁 가능한 싸움이지만, 네이버 쪽은 지도 앱의 SEO 개선만으로는 이길 수 없는 별개 채널입니다. 네이버 발견 경로를 원한다면 현실적인 방법은 지도 URL 자체를 네이버에서 순위 올리려는 것이 아니라, **운영자가 네이버 블로그에 리스티클을 직접 발행해서 카공맵으로 링크를 보내는 것**입니다(= 콘텐츠 마케팅, SEO 아님). 이 구분을 제품 결정에 반영해야 합니다.

## 2. 페이지 타입 미스매치 판정

- **대상 페이지 분류**: Tool / Interactive (taxonomy 우선순위 규칙 1번 — 기능하는 인터랙티브 지도가 있으면 최우선으로 Tool로 분류). 사람에게는 좋은 UX지만, 초기 HTML에 텍스트가 19단어뿐이고 스키마가 0개라 검색엔진 입장에서는 사실상 빈 페이지입니다.
- **SERP 지배 유형**: Local(디렉토리) + Blog(리스티클) 혼합, 약 90% 신뢰도.
- **미스매치 심각도: CRITICAL.**
  - 타입 자체가 어긋난 것(Tool vs Local/Blog)에 더해, 크롤링 가능한 콘텐츠가 사실상 존재하지 않는다는 이중 문제입니다. 지금 noindex인 것과 별개로, **noindex를 지금 당장 풀어도 이 구조로는 순위에 들 수 없습니다** — 구글이 읽을 텍스트가 없기 때문입니다.
  - 이건 "지도를 없애라"는 뜻이 아닙니다. 지도는 이 제품의 핵심 가치이고 사용자 경험상 옳은 선택입니다. 문제는 지도만 있고 **그 밑에 크롤링 가능한 콘텐츠 층이 없다**는 것입니다.

### 최소 형태 변경 (minimum shape change)

지도 셸을 걷어내거나 목록형 UI로 갈아엎을 필요는 없습니다. DESIGN.md의 "동작 안 하는 검색바를 먼저 띄우지 않는다"는 원칙과도 상충하지 않습니다. 필요한 것은:

1. **SSR로 렌더되는 크롤링 가능한 카페 목록 블록 추가.** 지도 아래(스크롤 시 보이는 영역)에 9곳의 이름·주소·콘센트/와이파이/소음/좌석/영업시간·확인일(last_verified)을 실제 텍스트로 렌더합니다. 지도가 여전히 첫 화면(above-the-fold)을 차지해도 됩니다 — CLAUDE.md의 "지도는 100dvh 풀스크린" 원칙을 건드리지 않습니다. 숨김 텍스트(display:none)로 채우면 안 됩니다 — 실제로 보이는 콘텐츠여야 합니다.
2. **`LocalBusiness`(또는 `Place`) JSON-LD를 카페별로 추가.** 현재 0개입니다. 이것만으로도 "콘센트 있는 카페 송파" 같은 속성형 쿼리에서 리치 결과 후보가 될 여지가 생깁니다.
3. **H1을 서술형으로 바꾸거나 H2 구조를 추가.** 지금 H1은 브랜드명 하나뿐이라 어떤 의도에도 매칭되지 않습니다.
4. (2차, 더 큰 변화) **카페별 개별 경로**(`/cafe/[slug]`)를 만들어 지도로 딥링크. "OO역 콘센트 있는 카페"류 롱테일에 개별적으로 순위를 노릴 수 있게 됩니다. 지금 아키텍처(카페별 URL 없음)를 바꾸는 일이라 스코프가 크므로 1~3을 먼저 하고 이건 다음 단계로 미뤄도 됩니다.

이 넷 중 1~3은 검색/필터 UI(2차로 보류된 것)와 무관합니다 — **"발견 가능한 정적 콘텐츠"와 "동작하는 검색 UI"는 다른 문제**이고, 전자는 지금 당장 해도 스코프 원칙을 어기지 않습니다.

## 3. 유저 스토리 (SERP 신호 기반)

1. **카페 투어 콘텐츠 소비자** (Awareness) — 여러 곳을 한눈에 비교하고 싶어서, 리스트/카드 형태를 기대하지만, 카공맵엔 목록이 없어 막힙니다.
   *근거: diningcode "Top100" 리스트, 에스콰이어·씨티매거진의 "OO곳 카페 투어" 매거진 글이 상위 지배.*

2. **콘센트 확인 강박이 있는 실사용자** (Decision) — 헛걸음을 피하려고 자리마다 콘센트가 있는지 방문 전에 확실히 알고 싶어 하지만, 이 정보가 지도 클릭 전에는 검색엔진에 전혀 노출되지 않아 막힙니다.
   *근거: diningcode 콘텐츠에 "각 자리마다 콘센트가 있다"는 구체적 서술이 그대로 상위 노출.*

3. **커뮤니티 후기를 신뢰하는 탐색자** (Consideration) — 익명 커뮤니티의 1인칭 경험담(소음 수준, 눈치 안 보임 여부)을 읽고 판단하고 싶어 하지만, 카공맵엔 후기 텍스트가 전무해 막힙니다.
   *근거: 블라인드·인스티즈·threads.com 게시물이 4개 쿼리 전부에서 상위권.*

4. **여러 동네를 넘나드는 노마드 워커** (Awareness→Consideration) — 지역별로 흩어진 블로그 글 대신 송파·잠실·강남을 아우르는 종합 지도를 원하지만, 지도가 noindex라 검색으로는 이 서비스의 존재 자체를 찾을 방법이 없어 막힙니다.
   *근거: 경쟁 서비스 zakgong.com(강남·서초·성동·광진 커버)이 언급됨, nomadrang.com이 지역별로 매번 "카페 5곳"을 새로 정리.*

5. **즉흥적으로 당일 카페를 정하는 사람** (Decision, near-me) — 지금 당장 가까운 곳을 원하지만, 카공맵이 검색엔진에 없어 "카공 카페" 류 검색으로는 발견 경로가 아예 없고 링크 공유로만 진입 가능해 막힙니다.
   *근거: "역 몇 번 출구", "근처" 등 위치 기반 표현이 다수 결과 제목/본문에 반복.*

Awareness / Consideration / Decision 세 단계를 모두 포함합니다.

## 4. 페르소나 스코어링

⚠️ 페이지가 현재 noindex라 실제 도달 자체가 불가능합니다(모든 항목이 사실상 0). 아래는 **"noindex를 풀고 위 2절의 최소 변경 전, 현재 구조 그대로" 라는 가정 하의 준비도 점수**입니다 — 지금 물어야 할 것은 "지금 상태로 풀면 몇 점이냐"이기 때문입니다.

| 페르소나 | 여정 단계 | Relevance | Clarity | Trust | Action | Total | 등급 |
|---|---|---|---|---|---|---|---|
| 카페 투어 콘텐츠 소비자 | Awareness | 14/25 | 6/25 | 5/25 | 8/25 | 33/100 | Critical Mismatch |
| 콘센트 확인러 | Decision | 18/25 | 7/25 | 8/25 | 6/25 | 39/100 | Critical Mismatch |
| 커뮤니티 후기 신뢰파 | Consideration | 10/25 | 5/25 | 4/25 | 6/25 | **25/100** | Critical Mismatch |
| 노마드 워커(지역 확장) | Awareness→Consideration | 12/25 | 8/25 | 5/25 | 7/25 | 32/100 | Critical Mismatch |
| 즉흥 당일 방문자(near-me) | Decision | 15/25 | 12/25 | 6/25 | 10/25 | 43/100 | Needs Work |

### 최약 페르소나: 커뮤니티 후기 신뢰파 (25/100)
**핵심 문제:** 카공맵에 1인칭 경험담·후기 텍스트가 전혀 없습니다. "왜 이 9곳을 큐레이션했는가"에 대한 근거도 화면에 없습니다.
**권장 조치:** 카페별로 큐레이터의 짧은 코멘트(1~2문장, 왜 이 카페를 골랐는지)를 텍스트로 노출하고, `last_verified`를 UI뿐 아니라 크롤링 가능한 텍스트로도 노출합니다.

### 눈에 띄는 사실: 즉흥 당일 방문자가 최고점(43/100)
지도 자체의 UX(클릭→상세→정보 확인 흐름)는 실제로 훌륭합니다. 이 페르소나의 병목은 **온페이지 품질이 아니라 발견 가능성**입니다 — 검색으로 도달하는 경로가 없다는 것. 즉, 카공맵의 문제는 "화면이 나쁘다"가 아니라 "화면까지 아무도 검색으로 못 온다"는 것에 훨씬 가깝습니다.

### 시스템적 이슈
- **Clarity와 Trust가 전 페르소나에서 공통으로 낮습니다.** 원인은 하나입니다 — 크롤링 가능한 텍스트가 19단어뿐이고 스키마·후기·근거 텍스트가 0개라는 것. 2절의 "SSR 콘텐츠 층 + schema" 하나가 이 두 축을 동시에 끌어올립니다.

### 우선순위 액션
1. SSR 크롤링 가능한 카페 목록 블록 추가 (전 페르소나의 Clarity 개선)

## 6. `work_policy` 도입이 검색 성과를 바꿀까 — 실제 의견

**결론부터: 조건부로 그렇습니다. 필터 UI로 만들면 검색 성과에 거의 영향이 없고, 카페별로 보이는 텍스트/스키마 속성으로 만들면 실질적인 SEO 효과가 있습니다.**

근거:

- SERP에서 실제로 확인됩니다 — 강남 카페공명 콘텐츠는 "눈치 보지 않고, 오랜 시간 집중하며 작업하고 공부하기 좋고요"라는 표현을 명시적으로 씁니다. 블라인드·인스티즈 게시물들도 "여기 카공해도 되나요" 류의 사회적 허들에 대한 질문/답변 패턴이 반복됩니다. 즉 `work_policy`(환영/허용/눈치/금지)가 scope.md에서 "가장 차별적"이라 규정한 것은 내부 가설이 아니라 **SERP에서 이미 관찰되는 실제 검색 의도**입니다 — 3절 유저스토리 3번(커뮤니티 후기 신뢰파)이 정확히 이 축입니다.
- 하지만 이게 **검색 순위에 반영되려면 크롤링 가능한 텍스트여야 합니다.** 지도 위 필터 토글로만 구현하면(클라이언트 사이드 인터랙션) 구글은 오늘과 똑같이 아무것도 못 읽습니다 — 필터는 발견 후의 UX 개선이지 발견 자체를 돕지 않습니다.
- 반대로, `work_policy` 값을 카페별로 "카공 허용도: 환영" 같은 **눈에 보이는 텍스트**로, 2절에서 이미 권장한 SSR 콘텐츠 층 안에 콘센트·소음과 나란히 넣으면 이야기가 달라집니다. 지금 SERP의 diningcode·블로그 어느 쪽도 이 속성을 "비교 가능한 구조화된 값"으로 노출하지 않습니다 — 다들 산문 속에 흩어진 서술("눈치 안 보임")로만 존재합니다. 즉 **"카공 눈치 안 보이는 카페 송파" 같은 롱테일에 답이 되는 페이지가 지금 SERP에 사실상 없습니다.** 이건 실제 콘텐츠 공백이고, 채우면 순위 기회가 됩니다.

**권장 순서:** 필터 UI(2차 보류)는 그대로 미뤄도 됩니다. 하지만 **데이터 모델(enum 컬럼)과 "카페별로 항상 보이는 텍스트 렌더링"은 지금 결정하고 지금 채워도 됩니다** — 이건 scope.md가 미룬 "동작하는 검색 UI"가 아니라 2절에서 이미 필요하다고 한 "크롤링 가능한 콘텐츠 층"의 일부이기 때문입니다. 단, `work_fit`처럼 큐레이터 주관이 섞이는 값이라 **판정 기준(무엇을 보고 환영/허용/눈치/금지를 가르는지)을 명확한 룰로 문서화**해야 합니다 — 애매하면 Trust 점수를 오히려 깎습니다.

## 7. 한계 (이번 분석에서 확인하지 못한 것)

- WebSearch 도구는 구글 색인 기반 요약입니다. 실제 SERP의 광고 밀도, PAA 박스 정확한 문구, 피처드 스니펫 포맷, AI Overview 인용 소스는 직접 확인하지 못했습니다 — 상위 링크 구성과 스니펫 텍스트로 유추했습니다.
- **네이버 검색 결과는 이번 세션에서 직접 조회하지 않았습니다** (WebSearch는 구글 전용). 6절·1절의 네이버 관련 서술은 한국 로컬 검색 생태계에 대한 일반 지식에 근거하며, 실시간 네이버 SERP 캡처는 아니었습니다.
- diningcode·매거진·커뮤니티 상위 링크들은 제목/스니펫만 확인했고, `render_page.py`로 직접 렌더링해 페이지 타입을 완전히 검증하지는 않았습니다.
- `render_page.py --mode auto`가 카공맵의 지도/마커 DOM을 완전히 캡처하지 못했습니다(안정화 임계값 미달). head·초기 HTML은 curl 정적 셸로 보강했지만, JS 상호작용 이후에만 나타나는 카페 사진·마커 텍스트는 이번 분석 대상에 포함되지 않았습니다.
- 대상 페이지가 noindex라 현재 실제 구글 순위는 존재하지 않습니다(예상대로). 4절 페르소나 점수는 "noindex 해제 + 현재 구조 유지" 가정의 추정치입니다.
