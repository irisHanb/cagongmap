## 합의된 전제

리서치 보고서를 바탕으로 한 논의에서 확정된 방향:

| 항목 | 결정 |
|---|---|
| **1차 목표** | 가설 검증용 MVP (얇게, 빠르게) |
| **데이터 수급** | 운영자 직접 시드 (크롤링 금지 — `mvp-decisions.md` 2-1) |
| **플랫폼** | 웹 (모바일 웹 우선) / Next.js App Router, 포트 3030 |
| **지도 SDK** | **카카오맵 JavaScript SDK** (확정) |

| **타겟 세그먼트** | 특정 안 함 (전체) — 단, 필터는 공통 1순위만 |
| **UGC(로그인·제보)** | **최종 목표에 포함. 단, 단계적 도입** — 로그인·북마크(2026-08-15), 리뷰·제보 **입력**(2026-08-20), **검수·장소 관리 화면**(2026-08-21) 순으로 들어왔다 |

핵심 전략: UGC에만 의존하지 않고 **작업 적합성 핵심 데이터를 운영자가 시드로 구축**한 뒤, **단일 권역**부터 시작한다.

## ✅ 이번 구현에서 먼저 다룰 기능

1. **지도 기반 카페 탐색** — 모바일 웹, 지도 위에 시드 카페 핀 표시. **송파·잠실** 권역으로 한정.
2. **핵심 필터** — 현재 시드 스키마 기준으로 확정 (아래 스키마 절 참고).
   - 콘센트(`outlet`) · 와이파이(`wifi`) · 소음(`noise`) · 지금 영업중 · 가격대(`iced_americano_price`)
   - ⚠️ 당초 3대 핵심 필터 중 하나였던 **카공 허용은 보류**되었다. 아래 "보류된 차별점" 참고.
3. **카페 상세 카드** — 핀 클릭 시 핵심 속성 + 영업시간 + 네이버 플레이스 링크 + "최근 확인됨"(`last_verified`) 표시.
   - 사진은 직접 호스팅한다 — 마커에 대표 사진, 상세에 좌우 슬라이드 (`mvp-decisions.md` 3절).
     ⚠️ 현재 이미지는 연습용 임시본이라 공개 전 교체가 필요하다.
4. **필터링 / 정렬** — 속성으로 핀을 거르고, 리스트 뷰로도 열람.
5. **운영자 시드 데이터 입력 구조** — 정적 `data/cafes.json` 직접 편집. 관리 화면은 만들지 않는다.
6. **UGC 입력 3종** (2026-08-20 추가) — 전부 로그인 필요.
   - **리뷰** — 기존 장소를 `good`/`normal`/`bad`로 평가. 1인 1건, 다시 누르면 해제.
     집계만 공개하고 누가 눌렀는지는 아무에게도 보이지 않는다(큐레이터 포함).
   - **수정 요청** — 기존 장소에 사진과 메모를 붙여 보낸다 (`place_edit_requests`).
   - **새 장소 제보** — 네이버 URL·사진·메모 (`place_reports`).
   - **카페 관련 이미지는 전부 `place-images` 버킷 하나를 쓴다.** 검수 전 사진은
     `submissions/<uid>/` 아래에 있다가 승인되면 `<slug>/`로 옮겨간다.
     `places.photos`는 경로를, 제보 두 테이블의 `photos`는 검수자가 바로 열 수 있게
     공개 URL을 담는다.
   - **제보와 수정 요청은 다른 정보라 테이블도 다르다.** 제보는 네이버 URL이, 수정
     요청은 대상 카페가 필수다 — 한 테이블에 두면 그 둘 다 nullable이 된다.
   - ⚠️ **제보는 그것만으로 카페가 되지 않는다.** `places`는 이름·주소·좌표·영업시간이
     not null이라, 큐레이터가 카페를 만든 뒤 제보를 연결한다. 수기 큐레이션 결정의 연장이다.

### 구현 순서

1차 구현은 **1번(지도 + 마커 + 상세 카드)까지**만 다룬다. 필터는 2차.
**리스트는 2026-08-26에 1차로 옮겼다** — dock 하단의 카페 전체 목록이고, 같은 날
그 위에 검색 입력칸도 넣었다 (아래 변경 이력, `DESIGN.md` Left Panel 7번). 정렬과
필터는 그대로 2차다.
상세 단계는 [implementation-plan.md](./implementation-plan.md) 5절 참고.

## ⏸️ 지금은 미뤄도 되는 기능

- **실시간 혼잡도 / 좌석 정보** — 데이터 소스 없음, 구현 난이도 높음. 가설 검증 단계에선 과함.
- ~~**UGC(사용자 제보 / 등록)**~~ → **2026-08-20에 1차로 옮겼다.** 아래 "이번 구현에서 먼저 다룰 기능" 6번 참고.
  - 옮긴 것은 **입력(제출)까지**였다. 검수 화면은 2026-08-21에 `/admin`으로 들어왔다.
    그 전까지는 승인·반려를 Supabase 대시보드에서 `approve_place_report()` / `approve_edit_request()`와
    그 반려 함수로 한다.
- ~~**제보 검수 화면(`/admin`)**~~ — **2026-08-21에 만들었다.** `/admin/reports`(검수)와 `/admin/places`(장소 추가·수정·사진)다. 앞당긴 이유는 제보 건수가 아니라 **장소 등록 자체가 대시보드 SQL 말고는 경로가 없었기 때문**이다 — 컬럼 19개짜리 insert를 손으로 쓰고 좌표를 복사해 오는 일이 시드 데이터 수집의 병목이었다.
- **폐업 신고** — 화면이 없어 쓰인 적이 없다. 2026-08-20에 제보 테이블을 가르면서
  `kind='closed'` 자리도 없앴다. 필요해지면 `place_closure_reports`를 따로 만든다.
- **제보 인센티브(포인트·뱃지), 신고 / 검증 기능**
- **수익화(광고·송객 제휴)** — 트래픽 임계량 도달 후. 단 업주 이해충돌 이슈가 있음 (`research-verification.md` 2절).
- **권역 확장, 네이티브 앱, 푸시 알림**
- **마커 클러스터링** — 현재 시드 9곳 규모에선 불필요.

## 📍 필요한 장소 데이터 (카페당 시드 스키마)

**현재 `data/cafes.json`의 실제 필드를 기준으로 확정한다.** (별도 스키마를 새로 설계하지 않는다)

| 필드 | 타입 | 비고 |
|---|---|---|
| `id` | string | **추가 예정** — 마커/리스트/상세 연결 키. 이름은 바뀌므로 키로 쓰지 않는다 |
| `name` / `address` / `lat` / `lng` | 필수 | 지도 핀 |
| `outlet` | enum (`many`/`some`/`few`/`none`) | 핵심 필터 1 — 현재 시드엔 `many`/`some`만 등장 |
| `wifi` | boolean | 핵심 필터 2 — 3단계가 아닌 유무만 |
| `noise` | enum (`quiet`/`normal`/`noisy`) | 핵심 필터 3 |
| `work_fit` | enum (`good`/`ok`/`bad`) | 종합 작업 적합도 |
| `open_time` / `close_time` / `is_24h` | string / boolean | 심야·24h 및 "지금 영업중" 판정 |
| `iced_americano_price` | number | 가격대 필터 |
| `naver_place_url` | string | 메뉴·리뷰 등 나머지 상세는 여기로 위임 |
| `tags` | string[] | 자유 태그 |
| `last_verified` | date | **추가 예정** — 신선도 표시 (`mvp-decisions.md` 2-3) |

→ 좌표·주소·영업시간은 공개 정보로 보강 가능하지만, **`outlet`·`noise`·`work_fit`은 운영자가 직접 채워야 하는 핵심 자산**이다.

### ✅ 되살린 차별점 — `work_policy` (카공 허용)

이전 버전의 이 문서는 **카공 허용(환영/허용/눈치/금지)**을 "3대 핵심 필터 중 가장 차별적"인 항목으로 규정했다가 보류했다.
**2026-08-21에 도입으로 결정했다** (미확정 이슈 ② 종결).

- `work_fit`은 대용이 되지 않는다. **"작업 환경이 좋은가"(환경 품질)와 "눈치 안 보고 있어도 되는가"(매장 정책)는 다른 정보**다.
- 되살린 근거는 SEO 감사의 SERP 역분석이다. 대상 쿼리 상위 결과에 "눈치 안 보임"류 표현이
  실제로 반복 등장한다 — "가장 차별적"이라는 당초 주장이 검증됐다
  (`seo-audit-2026-08-21/seo-sxo.md`).
- **필터 UI로만 만들면 효과가 없다.** 클라이언트 상호작용은 검색엔진이 읽지 못한다.
  카페마다 **항상 보이는 텍스트**로 적어야 의미가 있다. 그래서 필터(2차)를 기다리지 않고
  Quick Check 표시부터 넣었다.
- **값은 비어 있다.** 컬럼은 처음부터 nullable로 있었고(`db-schema.md`), 시드 9곳은 전부 null이다.
  카공 허용도는 매장에 가 봐야 아는 값이라 **추측으로 채우지 않는다.** 값이 있는 카페에만 화면에 나온다.
- 남은 일은 9곳을 실제로 확인해 값을 매기는 것이다. → 운영자 확인 항목 2번(시드 데이터 수집)과 같은 병목이다.

## ⚠️ 사용자(운영자)가 직접 확인해야 할 가정

1. ~~**권역 선택**~~ → **해결됨.** 송파·잠실로 확정 (기존 시드 9곳 중 7곳이 해당).
   - 권역 밖 2곳(스타벅스 삼성교점, 테라로사 포스코센터점 — 강남구)은 삭제하지 않고 유지한다. 초기 지도 중심을 송리단길로 두면 화면에 안 잡힐 뿐이다.
2. **시드 데이터 수집 방법의 현실성** — **미해결. 여전히 MVP 최대 병목.**
   - 현재 9곳. 목표 규모(50~100곳)까지 어떻게 채울지 미정.
   - 크롤링은 약관 위반으로 배제됨 (`mvp-decisions.md` 2-1) → 직접 방문 또는 리뷰 수기 조사만 남는다.
3. **작업 적합도 판정 기준** — **미해결.** 현재 시드의 `work_fit` / `noise` 값을 직접 방문으로 매겼는지, 리뷰를 보고 추정했는지가 문서화되어 있지 않다. 이 라벨의 신뢰도가 서비스 신뢰도를 좌우한다.
4. ~~**지도 SDK 선택**~~ → **해결됨.** 카카오맵 JS SDK. 무료 쿼터는 계정의 첫 활성화 앱 1개 한정 (`mvp-decisions.md` 2-2).
5. **카카오 콘솔 플랫폼 도메인 등록** — `http://localhost:3030` 등록 필요. 포트가 3030이므로 기본값 3000으로 등록했다면 지도가 뜨지 않는다.

## 변경 이력

**2026-08-26** — dock 카페 전체 목록 위에 검색을 넣었다
- 이름·주소 부분 일치로 목록과 지도 마커를 **함께** 거르는 검색 입력칸을 카페 전체
  목록 상자 안에 넣었다. 필터 판정은 `lib/cafe-search.ts` 한 곳에 있다.
- **`DESIGN.md` Left Panel 4번(브랜드와 로그인 사이)에 잡아 둔 검색바 자리를 7번
  카페 전체 목록 상자 안으로 옮겼다.** 검색이 목록 없이 단독으로 쓰이지 않으므로
  별도 순서를 차지할 이유가 없다는 판단이다.
- 필터·정렬 UI, 초성 검색, 검색어 URL 동기화는 그대로 2차다 — 검색 범위는 이름·주소
  부분 일치뿐이다.

**2026-08-26** — 카페 전체 목록을 dock 하단에 넣었다
- **리스트 뷰를 1차로 이동.** "필터·리스트 뷰는 2차"와 `DESIGN.md`의 "후보 카페 리스트
  제거"를 함께 뒤집는다. 필터와 정렬은 그대로 2차다.
- 근거: 지도에는 **지금 화면에 든 마커만** 보인다. 카페가 10곳인데 초기 중심에서
  보이는 것은 그중 일부이고, 나머지를 찾으려면 지도를 옮겨 보는 수밖에 없었다.
  `/cafes`가 전부를 보여주지만 **지도를 떠나야** 하고, 거기서 카페를 고르면 지도로
  돌아오는 길이 없다.
- 제거의 근거였던 "목록이 지도를 밀어낸다"는 목록이 dock을 넘어 자라날 때만 성립한다.
  목록 자체가 스크롤하므로 카페가 늘어도 dock 높이는 그대로다 (`DESIGN.md` Left Panel 7번).
- `/cafes`는 남는다. 저쪽은 크롤러와 LLM이 읽는 서버 렌더 문서라 목적이 다르다
  (2026-08-21 SEO 감사).

**2026-08-20** — 리뷰·제보 입력을 1차 범위로 이동
- **리뷰와 제보(수정 요청·신규)를 1차에 포함**으로 변경. 2026-08-15에 "제보·리뷰는 여전히
  제외다. 그쪽은 콜드스타트가 그대로 걸린다"고 적은 것을 뒤집는다.
- 근거: 데이터 수급이 여전히 최대 병목(위 가정 2번)인데, 운영자 직접 방문 외에 경로가
  없다. 크롤링은 약관으로 막혀 있고 시드는 9곳에서 멈춰 있다. **사용자가 밀어 넣을 입구를
  열지 않으면 이 병목은 구조적으로 풀리지 않는다.**
- 콜드스타트는 여전히 사실이다. 대신 **빈 상태를 숨기지 않는 방식으로** 감당한다 —
