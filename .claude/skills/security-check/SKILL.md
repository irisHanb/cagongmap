# 카공맵 보안 점검

이 저장소는 anon 키가 브라우저에 그대로 나가는 구조다. 그래서 **앱 코드의 검사는 안내이고
방어선은 DB(RLS·check 제약·storage 정책)와 서버 액션의 `requireCurator()`뿐이다.**
점검의 축이 그것이다 — 화면이 막는 것을 세지 말고, 화면을 건너뛰었을 때 무엇이 남는지를 센다.

선례가 있다. `docs/security-audit-2026-08-23/README.md`가 같은 형식으로 끝난 이전 감사다.
**시작할 때 그 문서를 먼저 읽는다** — 이미 처리된 것을 다시 발견해 올리지 않기 위해서고,
6절 「사람이 결정할 것」이 아직 열려 있어 그 상태를 이어받아야 하기 때문이다.

## 1. 시작 — 방식을 먼저 묻는다

다른 무엇보다 먼저 `AskUserQuestion`으로 묻는다. 임의로 고르지 않는다 — 3번은 안전하지만
1번은 남의 서버에 요청을 보내는 일이라 사람의 승인이 필요하다.

> 어떤 방식으로 보안 점검을 진행할까요?
> 1. 운영/Preview URL을 직접 테스트
> 2. 로컬 서버를 켜서 테스트
> 3. 로컬 코드만 점검

**1번을 골랐으면 두 가지를 확인한 뒤에야 요청을 보낸다.**

- URL이 무엇이고 **사용자 소유가 맞는지**
- 그 URL에 **점검 요청을 보내도 되는지** (Vercel Preview라도 확인한다)

둘 중 하나라도 답이 흐리면 요청을 보내지 않고 3번으로 내려간다. 남의 서버를 찔러 보는 것과
내 서버를 확인하는 것은 다른 일이고, 그 판단은 사람이 한다.

## 2. 정적 검사 — 방식과 무관하게 항상 먼저

동적 점검은 정적 검사가 세운 가설을 확인하는 수단이다. 순서를 뒤집으면 "요청을 보내 봤더니
403이 나왔다"만 남고 **왜 막혔는지, 다른 경로로는 열려 있는지**를 모른 채 끝난다.

읽을 자리는 이 저장소에서 정해져 있다.

| 무엇 | 어디 |
|---|---|
| 라우트·페이지 | `app/**/page.tsx`, `app/**/route.ts`, `app/**/actions.ts` |
| 권한 경계 | `lib/admin/guard.ts`, `proxy.ts`, 각 서버 액션의 첫 줄 |
| 데이터 접근 | `lib/cafes.ts` · `bookmarks.ts` · `reviews.ts` · `submissions.ts` · `lib/admin/*.ts` |
| RLS·제약·storage 정책 | `supabase/migrations/*.sql`, 요약표는 `docs/db-schema.md` |
| 환경변수 | `lib/supabase-env.ts`, `lib/site.ts`, 저장소 전체의 `process.env` |
| 클라이언트 경계 | `'use client'` 파일이 무엇을 import하는가 |

훑는 명령은 이 정도면 된다. 결과가 없다는 것도 소득이니 빈 결과를 그냥 넘기지 않는다.

```bash
grep -rn "process.env" app lib components scripts proxy.ts next.config.ts
grep -rln "'use server'" app lib          # 서버 액션 파일
grep -rn "requireCurator\|guardAdminPage" app lib   # 가드가 빠진 곳 찾기
grep -rn "enable row level security\|create policy\|with check" supabase/migrations
grep -rn "service_role\|SERVICE_ROLE" app lib components   # 앱에 들어와선 안 된다
```

### 2-1. 사용자 권한 관점

한 사용자가 다른 사용자의 것에 닿을 수 있는가를 본다.

- **인증·인가** — 보호돼야 할 라우트가 실제로 세션을 확인하는가. Next는 레이아웃과 페이지를
  동시에 렌더하므로 **레이아웃 가드만으로는 페이지 RSC 페이로드가 새어 나간다.**
  페이지마다 첫 줄에 가드가 있는지 본다.
- **소유자 확인** — 소유자 컬럼 이름이 테이블마다 다르다(`profiles.id`,
  `bookmarks.user_id`, `place_reports.submitted_by`). 이름을 가정하지 말고 스키마를 본다.
- **관리자 접근** — 판정이 `profiles.role in ('curator','admin')` 한 곳인가.
  **서버 액션은 레이아웃 가드 뒤에 있지 않다** — POST로 직접 부를 수 있으므로 액션마다
  `requireCurator()`가 첫 줄이어야 한다.
- **파일 접근** — `place-images`는 공개 버킷이다. 검수 전 사진(`submissions/<uid>/`)의
  경로 규칙, 업로드 상한, 남의 폴더에 쓰기·읽기를 storage 정책이 막는지 본다.
- **RLS** — `SELECT`/`INSERT`/`UPDATE`/`DELETE` 넷을 각각 본다. **`UPDATE`는 `using`과
  `with check`를 같이** 본다 — `with check`가 없으면 본인 row의 role을 스스로 올리는
  경로가 열린다. 정책이 자기 테이블을 select해 재귀하지 않는지도 함께 본다.
- **입출력 필드 제한** — `select('*')`로 필요 이상을 내보내는 곳, 클라이언트가 보낸 값을
  그대로 insert하는 곳. **브라우저의 검사와 DB의 check 제약이 짝이 맞는가**가 핵심이다.
  한쪽만 있으면 그건 검사가 아니다.

### 2-2. 서비스 운영 관점

서비스가 스스로 감당하지 못하게 되는 경로를 본다.

- **API 키·환경변수 노출** — `NEXT_PUBLIC_`이 붙은 것은 전부 공개다. 붙지 말아야 할 것에
  붙어 있지 않은지(특히 `SUPABASE_SERVICE_ROLE_KEY`), `.env*`가 git에 들어가지 않았는지.
- **오류 응답** — 제약 이름이 박힌 Postgres 오류나 스택 트레이스가 화면·응답에 그대로
  나가지 않는지.
- **rate limit과 과금 상한** — 업로드·제보·리뷰·지도 SDK 호출에 상한이 있는지. 없으면
  없다고 적는다. 카카오맵 쿼터와 Supabase storage 용량이 실제 비용선이다.
- **환경 분리** — 운영과 로컬이 같은 Supabase 프로젝트를 보고 있는지.
- **백업·복구** — 있는지 없는지. 있다면 복구를 해 본 적이 있는지.
- **사고 대응** — 키가 샜을 때 무엇을 돌리면 되는지가 적혀 있는지.

## 3. 동적 점검 — 범위가 고정이다

**1번(운영/Preview)**: 허가를 받은 뒤 `curl`이나 `playwright-cli`로 **비파괴 요청만.**
**2번(로컬)**: `npm run dev`(포트 3030 고정)를 띄우고 `http://localhost:3030` 기준으로 같은 것을 본다.
**3번(코드만)**: HTTP 요청을 **한 건도 보내지 않는다.** 대신 위험 후보와 **작성해야 할
실패 테스트**를 정리한다. 여기서 나온 테스트는 그대로 4절의 「반복 점검할 것」이 된다.

보내도 되는 요청은 이것뿐이다.

1. **비로그인으로 보호 페이지** — `/admin`, `/admin/reports`, `/admin/places`가 404인가.
   상태 코드만 보지 말고 **응답 본문에 데이터가 실려 있지 않은지** 확인한다
   (2026-08-21에 404 응답 37KB 안에 카페 이름과 주소가 있었다).
2. **일반 사용자로 관리자 경로와 관리자 API** — 페이지와 서버 액션 엔드포인트 양쪽.
3. **id·path를 바꿔 남의 데이터** — 다른 사용자의 북마크·리뷰·제보 row를 PostgREST로 직접
   읽어 본다. 읽기(select)까지만이다.
4. **private 파일 직접 URL** — `submissions/<남의 uid>/...`를 URL로 직접 열어 본다.
5. **오류 응답의 민감 정보** — 잘못된 입력을 하나 넣고 돌아오는 메시지를 본다.
6. **가벼운 rate limit 확인** — 같은 요청 **5~10회 정도.** 그 이상은 부하 테스트이지
   점검이 아니다.

**하지 않는 것.** 대량 요청, 파괴적 요청(delete·drop·덮어쓰기), 실제 데이터 변경.
쓰기를 꼭 확인해야 하면 **트랜잭션 안에서 rollback**으로 한다
(`docs/security-audit-2026-08-23/README.md` 1절이 그 방식이다).
남의 계정으로 로그인하지 않고, **카카오 자격증명은 사람이 입력한다.**

## 4. 결과 형식

세 묶음으로 낸다. 각 항목은 **어디서 확인했는지**(파일:줄 또는 요청과 응답)를 달고,
관점 태그(`[사용자]` / `[서비스]`)를 붙인다. 근거가 없으면 "가능성"이라고 적는다 —
정적 검사에서 나온 가설과 실제로 확인한 것을 섞지 않는다.

```markdown
## 바로 고칠 것
결정이 필요 없는 것만. 무엇을 어디서 어떻게 고치는지가 한 줄로 나온다.
- [사용자] `app/admin/places/actions.ts:42` — `deletePlace`에 `requireCurator()`가 없다.
  첫 줄에 추가한다. (다른 액션 4개는 있다)

## 사람이 결정할 것
비용·정책·제품 판단이 걸려 무엇이 옳은지 코드가 정하지 못하는 것.
선택지와 각각의 대가를 적고, 고르지는 않는다.
- [서비스] 업로드 상한 — 지금은 폴더당 20장뿐이고 시간당 제한이 없다.
  (a) Supabase 무료 한도까지 두고 감시 (b) 제보 자체에 일일 상한.

## 반복 점검할 것
한 번 보고 끝낼 수 없어 자동화로 남겨야 하는 것. 실패 테스트가 가장 좋은 형태다.
- `supabase/tests/20_rls_checks.sql`에 "남의 북마크 select는 0행" 절을 `assert_eq`로 추가
- `./scripts/verify-schema.sh`를 커밋 훅이 아닌 배포 전 체크로 승격할지
```

빈 묶음은 비었다고 적는다. **아무것도 못 찾았으면 그렇게 말한다** — 채우려고 짜내지 않는다.

## 5. 마무리

- 발견이 있으면 **고치기 전에 이 세 묶음을 먼저 보여 준다.** 「바로 고칠 것」을 실제로
  적용할지는 사용자가 말한 다음이다.
- 감사 결과를 문서로 남길 때는 `docs/security-audit-<YYYY-MM-DD>/README.md`에
  **새 폴더로** 만든다. 기존 스냅샷은 특정 시점 기록이라 갱신하지 않는다.
- DB 정책을 바꿨으면 `docs/db-schema.md`의 RLS 요약표도 같은 작업에서 고친다.
